# LandIntel Investment Fit (jev) - design spec (DRAFT for operator review, not shipped)

Status: design and prototype. No external call is made; every result is a deterministic SAMPLE stub (`stubEngine.ts`). The prototype UI is `components/landintel/InvestmentFitPanel.tsx`; the deterministic modules stay the source of NUMBERS (`feasibilityScore.ts`, `investForecast.ts`, `investmentCase.ts`, `feasibilityReport.ts`, `parcelContext.ts`). jev only JUDGES; it never invents figures.

## 0. What the jev docs (docs.typesafe.ai) confirm, and what they do not
- CONFIRMED: `POST https://api.typesafe.ai/v1/systemone`, header `Authorization: Bearer <API_KEY>`, JSON body `{state, model:"jev-latest", questions:{name:{type,instructions,criteria?}}}`. Response `{model, answers:{name:{type, noul|choice|score, probabilities?, confidence?}}, usage:{input_tokens,output_tokens}}`. Noul = probability 0-1; Choice = `criteria` map of options, returns chosen option, probabilities, confidence; Score = ordered `criteria` array of 2-10 levels, returns weighted score, probabilities, confidence. Errors: 401 bad key, 422 malformed, 429/529 retry with backoff. Questions in one call run in parallel. Key comes from console.typesafe.ai/keys.
- CONFIRMED numbers: jev 1.13.0; USD 42 per billion input tokens (output free); limits 250,000 tokens/s and 1,200 requests/min; 64k context (32k state + longest question); text/JSON only; English best. Aliases `jev-latest` (stable), `jev-preview` (newest build; currently identical). Confidence guidance: above 0.9 act, 0.5-0.9 confirm, below 0.5 route away. No per-account fine-tuning: "shaped through requests" (state, instructions, criteria).
- Plain `fetch` from a Cloudflare Worker: it is one HTTPS POST with JSON, so it should work with no new dependency (package.json is protected, RULE 6). The docs do not mention Workers: UNVERIFIED until tested with a real key.
- Vercel AI Gateway: the docs describe NO gateway route and no gateway key handling: UNVERIFIED. Only the direct Bearer key is documented. Latency figures: UNVERIFIED (only a cookbook claim that batching questions is faster). Experimental status: not stated except the `jev-preview` alias and a "known issues" page (`model-jaggedness/jev-1.13`): treat `jev-latest` as production, re-read that page before go-live. Feedback, calibration or fine-tuning API: none documented: UNVERIFIED.

## 1. The preference registry (DATA, not code) and the parameters panel
`registry.ts` is the versioned list (`REGISTRY_VERSION 2026.09.19-1`); the UI, the state text and the result all read it. Entry = `{id, label, category, input(select|number|boolean|area|length|distance), options|min|max|step, unit, addedOn, status(draft|active|retired), consumedBy(suit|budget|return|verdict), stateLabel, core}`. Same definition-object pattern as `lib/workspace/controlRegistry.ts` (W-48), but a separate registry because that one is typed to studio building knobs. Adding a preference = adding an entry; no component change. Only `active` entries are selectable; new entries start `draft` and are reviewed before `active`. Dual units are automatic (RULE 30): area shows m2, sq ft, cents, guntha, ground, acres; length shows m and ft; distance shows km and mi.
- Ships with 65 active entries in 8 categories (Use and money, Site, Access, Utilities, Risk, Legal and title, Neighbourhood, Market). CORE (weighed by the stub arithmetic): intended use, budget min/max (INR crore), target return (% a year), holding period (years), risk tolerance, minimum plot area (m2), preferred zone, require VERIFIED record. Suggested defaults: use residential, budget 0.5-2 crore, 8% a year, 5 years, medium risk, 200 m2.
- Scaling UI (5 to 100+): search-or-add box, chips for chosen ones (first 8, then "Show all N"), values grouped in collapsible categories (first open), "More preferences (N available)" disclosure, saved sets (per-browser convenience only), "Suggest a preference". Screenshots at 5, 25 and 60 preferences hold at 1366x768 and 375x667.
- Every stated preference is written into the state text and listed in the details view with the judgment that reads it. The SAMPLE stub arithmetic only weighs the core ones; the real model would read all of them from the state.

## 2. The STATE template (`stateTemplate.ts`)
Plain text, two blocks: PARCEL FACTS then STATED REQUIREMENT. Facts: ULPIN, state, district; area as `m2 = sqft = cents = guntha = ground = acre`; land use, zone; current value (INR crore); feasibility score (0-100); growth assumption; projected value at end of hold (from `projectLandValue`); provenance (status, source, vintage). Requirement: the core fields, then `Other stated preferences: label=value; ...`. Any missing value is printed `UNKNOWN`; nothing is filled or defaulted. No personal data. User-suggested text (only after approval) appears only inside `[USER_PREFERENCE_TEXT]...[/USER_PREFERENCE_TEXT]`.

## 3. Judgments (`questions.ts`; thresholds are PROVISIONAL, to be validated on the golden set)
- `suit` Noul: "does this parcel plausibly suit the stated use". Above 0.75: shown as a fit; below 0.30: counts as a clear miss (drives "do not proceed"); between: needs conditions.
- `budget` Score, 5 levels (far above budget ... comfortably within): 4-5 good; 1-2 poor (level 1 drives "do not proceed").
- `return` Score, 5 levels (far below target ... clearly exceeds): 4-5 good; 1-2 poor. Growth is a user assumption, never a forecast.
- `verdict` Choice: proceed / proceed-with-conditions / do-not-proceed / insufficient-information. Insufficient when 3 or more of the 6 key facts (area, land use, zone, current value, feasibility score, growth assumption) are UNKNOWN. Proceed only when suit at least 0.75, budget and return at least 4, no UNKNOWN, and the record is VERIFIED if the user required it.
- HEADLINE SCORE (the only thing on the main page): `round(100 x (0.4 x suit% + 0.3 x budget% + 0.3 x return%))` where budget% = (level-1)/4. Bands: 70+ strong, 45-69 moderate, below 45 weak. When the verdict is insufficient-information the page shows "Not enough information" INSTEAD of a number. Confidence tiers per the docs: below 0.5 "do not rely", 0.5-0.9 "confirm", above 0.9 "high". Recommendation: show the number with its band word beneath (a bare number implies false precision; the band is the readable part), with a single small INDICATIVE chip.
- Main page shows only: score, band, INDICATIVE, "How was this score reached?". All sub-scores, thresholds, deterministic figures, feasibility score and the verdict wording are in the details view, which shows: the arithmetic (must equal the number shown, RULE 29), preferences used, each judgment with confidence, why and cited facts, source and freshness, UNKNOWN gaps, deterministic figures (feasibility score is the fallback if the model is unavailable), and versions (model, question set, registry, thresholds). Three allotments were built to choose from: inline in-flow under the score, true modal (page inert, focus trapped, Escape closes and returns focus), dedicated side region.

## 4. Guardrails (requirements)
Everything is INDICATIVE, never financial, legal or compliance advice (RULE 61(d)). Every judgment shows confidence, cited facts and why. UNKNOWN-heavy state yields "Not enough information", never a guess. jev never mutates a model or project state (RULE 50): read-only call, result is display data. What leaves the site: the rendered state (parcel facts and stated preferences only, no name, email, account or contact data). PRIVACY WORDING NEEDS THE OPERATOR'S REVIEW before any real call. Fallback: model down, timeout or low confidence shows the deterministic feasibility score only.

## 5. Integration plan (server-side only)
Browser posts `{parcel facts, preferences}` to a new Worker route; the Worker renders the state (this module's `renderState`), builds the request (`buildSystemOneRequest`), calls jev with plain `fetch`, validates the response shape, and returns the `FitResult` contract. `worker.ts` is PROTECTED and CRANE-only: REQUEST to CRANE: route `POST /api/landintel/investment-fit` (rate limit per IP and per session, e.g. 10 a minute; cache by hash of state + registry version + question-set version for 24 h; timeout 8 s; one retry with backoff on 429/529; on failure return `{fallback:true}`) and secret `TYPESAFE_API_KEY` (or the gateway key once the operator confirms the route). Token cost: a 65-preference state is roughly 1,500 tokens; at the published rate that is well under USD 0.001 per call (estimate, not measured).

## 6. Test plan
Golden set (versioned file, each case = facts + preferences + expected band): strong match; wrong use; over budget; below target return; VERIFIED required but record only INDICATIVE; UNKNOWN-heavy; all-UNKNOWN; 100 preferences; conflicting preferences; unit edge cases (0 m2, huge area); adversarial suggestion text. Unit tests exist for the stub, registry, state rendering, request shape, score reconciliation and the suggestion filter (`stubEngine.test.ts`, `InvestmentFitPanel.test.tsx`). Before go-live: run the golden set against the real model, compare bands, tune thresholds, record calibration.

## 7. Suggestion pipeline ("Suggest a preference")
UI: a collapsible in-flow block inside the preferences panel (screenshot `b-in-forecast-*-suggest-25prefs.png`). Flow: submitted -> analysing -> needs-data | approved | rejected | merged-into-existing. Backend analysis: dedupe against the registry; is it measurable; which judgment consumes it; DATA READINESS (does Ferrum have or can it source the fact? if not it stays `needs-data`, and any score using it shows that preference as UNKNOWN, never guessed); effect on the state text and questions. Operator approves; approval creates an `active` registry entry as a NEW registry VERSION. The user sees the status and, once approved, that it is now used.
Requirements: (i) POLICY FILTER: auto-reject and never send to the model preferences on protected or discriminatory attributes (caste, religion, ethnicity, community, gender and similar) or unlawful ones; borderline goes to human review (client first pass exists in `suggestion.ts`; the server list is authoritative). (ii) PROMPT-INJECTION SAFETY: suggested text is data only: length limit 120, control/zero-width/bidi characters stripped, instruction-like phrases rejected, rendered only inside the delimited field, cannot change questions, thresholds or behaviour; adversarial test set required. (iii) NO SILENT SCORE CHANGE: a new parameter is a new registry version; each result records the version used.

## 8. Self-learning (spec only; no learning code)
- What learns: only Ferrum's calibration AROUND jev (thresholds, weights, bands). The hosted model does not learn from Ferrum's calls; the docs document no feedback, calibration or fine-tune feature (UNVERIFIED; docs say it is shaped by requests).
- Capture: per result agree/disagree/why; outcomes when users report them (bought, passed, later value). Each stored score records model, question-set, registry and threshold versions, so it can be reproduced and audited.
- Ground truth problem: "worthy of investment" has no ground truth; proxies are user agreement and reported outcomes, both slow, sparse and biased toward users who act. Risks: feedback loops, selection bias, drift, gaming, discriminatory patterns.
- AUTOMATIC WITH A SAFETY CHECK: an update (thresholds and weights only, within bounds) goes live on its own ONLY if it passes the fixed GOLDEN SET: no band regression beyond a stated tolerance (proposed: 0 cases moving two bands, at most 5% moving one), calibration not worse, per-case score movement at most 5 points, policy and fairness checks pass, no change to which parameters are active. Otherwise it waits for human review. Automatic rollback on anomaly; rate limit on promotions (proposed: one a week); audit log of every version and why it was promoted; a KILL SWITCH file (modelled on DEPLOY_STOP / FLEET_WATCH_STOP in AGENTS.md) that freezes learning. NEW PARAMETERS always need operator approval (section 7).
- Measure "smarter" with golden-set metrics and calibration over time; never claim it.
- Privacy: consent, retention period and what is stored must be decided; storage needs a D1 table and migration, PROTECTED and CRANE-only: REQUEST to CRANE (tables: `fit_results`, `fit_feedback`, `registry_versions`, `suggestions`), not written here.
