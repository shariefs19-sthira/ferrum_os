## Part 1 — Self-learning generative-design architectures

| Component | What the research shows | Applicability to Ferrum |
|---|---|---|
| **Feedback-loop labelling** | Closed-loop "generation → evaluation" workflows are the dominant pattern: a design is generated, a human (or a lightweight reward model trained on minimal binary feedback) scores it, and the score feeds back into the next generation round. One cited approach (censored sampling for topology design) trains a reward model from just binary human preference signals, not dense ratings — a low-friction labelling design | Directly applicable to a future SUTRA option-chip flow: each chip selection (W-28) is *already* a binary preference signal (chosen vs. not chosen) — no new UI is needed to start collecting this, only a decision to log and use it |
| **Cohort priors** | Not found as a named, standardized technique in this research pass — likely refers to using aggregate preference statistics from a similar user segment (e.g. "3BHK buyers in Bengaluru") to bias initial generation before individual feedback exists. **Not independently verified as an established pattern under this exact name** — flagged rather than asserted |
| **LoRA / fine-tune staging** | LoRA (Low-Rank Adaptation) is the confirmed dominant lightweight fine-tuning pattern for aligning a base generative model to a narrow domain without full retraining — used in cited work both for architectural image generation (Stable Diffusion + LoRA + ControlNet for structural constraints) and general product-design aesthetic alignment from human feedback. Each LoRA module can target a single design element independently (a modular staging pattern, not one monolithic fine-tune) | **Only relevant if/when Ferrum adopts a generative image/render model** — Ferrum's core plan-generation engine is explicitly deterministic (`W-55`/`W-66`), not a diffusion model; LoRA staging would apply only to a future rendering/visualization layer, not the structural/compliance engine itself, and only after `W-31`'s LLM-seat gate clears |
| **Eval harnesses for design quality** | Two concrete evaluation patterns found: (1) **M-Judge**-style pairwise MLLM win-rate comparison (judge picks the better of two layouts on aesthetics/clarity/usability/creativity/consistency) — used where coordinate-level metrics can't capture holistic quality; (2) **LLM-as-judge with an agentic two-judge split** (a complexity judge + a quality judge scoring against source-grounded rubrics) — found in code-architecture evaluation, generalizable to design-layout evaluation. Caution found in the same research: LLM-as-judge alone is documented as **prone to bias and hallucination** for structurally complex outputs — not sufficient standalone | If Ferrum ever needs to evaluate generated-design quality automatically (e.g. auto-scoring `W-67`'s preset library beyond PLAN_AUDIT's pass/fail), a **hybrid** harness (structural/rule-based checks, which Ferrum already has via `PLAN_AUDIT`, plus an LLM-judge layer only for subjective qualities like aesthetics) matches the research's own caution against LLM-judge-only evaluation |

**Overall pattern match:** every architecture found in this research assumes a generative (diffusion/LLM-based) design engine at its core. **Ferrum's actual core engine is deterministic, not generative** — these patterns are relevant to a future, separate rendering/aesthetic layer, not a replacement for the existing structural/compliance engines. This is a real, load-bearing distinction, not a technicality.

## Part 2 — DPDP Act 2023 constraints on preference data

| Constraint | What the Act requires | Applicability to preference/cohort data |
|---|---|---|
| **Sensitive categories** | **The DPDP Act, unlike GDPR, does not define a special "sensitive data" category with extra protections** — this is a real, confirmed difference from GDPR/CCPA-style frameworks. All personal data is governed uniformly, not tiered | Simplifies classification (no separate "special category" bucket to design around) but does **not** reduce the consent/minimization obligations below — nothing in DPDP exempts preference data from being personal data if it's linked to an identifiable person |
| **Consent** | Consent must be free, specific, informed, unconditional, and unambiguous, given via clear affirmative action; **no secondary use or repurposing without fresh consent**; verifiable parental/guardian consent required for children and persons with disabilities | **Directly binding on any preference-learning system**: if a user's SUTRA interaction history is later repurposed to train a shared/cohort model (not just improve that same user's own session), that is very likely a *new purpose* requiring fresh, specific consent — the original "help me design my building" consent does not automatically cover "use my choices to train a model for other users" |
| **Data minimization** | Only data necessary for the stated purpose may be collected; data must be erased once the purpose is achieved or consent is withdrawn | A cohort-prior or fine-tuning dataset that retains preference data indefinitely, past the individual project's completion, is a minimization risk unless a separate, specifically-consented retention purpose is established |
| **Anonymization vs. pseudonymization** | **Anonymized data (irreversibly non-identifiable) is understood to fall outside DPDPA's scope; pseudonymized data (identifiers replaced but re-identification possible) remains within scope.** Confirmed technical approaches: randomization and generalization. **The Act itself does not specify concrete technical thresholds for what counts as "anonymized enough"** — a real, confirmed ambiguity, not a solved problem | If Ferrum wants to build cohort priors from aggregate preference data *without* per-user consent for that specific use, the data must be **genuinely, irreversibly anonymized** (not merely pseudonymized/de-identified) to fall outside the Act — and even then, the ambiguity in what counts as sufficiently anonymized is a real compliance risk the Act doesn't resolve for you |

**Net implication for a Ferrum feedback-loop design:** the safest compliant architecture is **per-user, purpose-scoped learning** (a user's own choices improve *that user's own* subsequent suggestions within the same consented purpose) as the default, with any cross-user cohort-learning or model-training use requiring **either** a separate, specific, freely-given consent captured at the point of collection, **or** genuine irreversible anonymization before aggregation — not an implicit ToS clause buried in onboarding.

## Part 3 — Competitor data practices vs. Ferrum's differentiator

**What could be independently verified this pass:** **nothing company-specific.** A targeted search for Maket.ai's and Higharc's actual privacy-policy language on AI training use returned no company-specific results — **this is a real research gap, not a finding**, and no claim about what either company actually does with user data should be made based on this pass. The general search results describe *industry-standard* practice (train-on-user-data-by-default with an opt-out, common in SaaS AI products) but **this is not evidence of what Maket or Higharc specifically do** — flagged rather than inferred.

**What is verifiable and real:** Ferrum's own current posture, checked against the codebase directly:
- No generative model exists in Ferrum's core engines today (`W-55`/`W-66` are deterministic) — there is currently **no user-preference-to-model-training pipeline of any kind to audit**, compliant or otherwise. This section's whole subject is prospective, not a description of something already running.
- SUTRA's demo mode is explicitly labeled "DEMO · INDICATIVE" (per prior session's direct source read of `SutraPanel.tsx`) — an existing honesty pattern that would extend naturally to a future "your choices help improve suggestions" consent notice, rather than a silent default.

**The differentiator, stated honestly:** Ferrum's standing architecture — deterministic engines, SUTRA as citation/routing only, every figure honesty-labeled and audited — means **there is no existing incentive or mechanism pulling user data into a shared training loop today**, unlike a platform whose core value proposition already depends on a generative model that improves from usage. This is a genuine structural advantage for a consent-first pitch, but it should be pitched as **"we don't have this problem yet because we haven't built the generative layer"**, not as **"we've solved a problem competitors haven't"** — those are different claims, and only the first is currently true.
